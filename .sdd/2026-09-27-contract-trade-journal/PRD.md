# Product Requirements Document (PRD) — 助理代記合約交易日誌

**Status:** Draft · **Version:** v1.0 · **Owner:** James Hsueh
**Stakeholders:** 交易服務（`go-trading` 同名切片，業務規則的唯一來源）、操作台（`go-trading-frontend` 同名切片）

---

## 1. Background & Goal

- **Problem Statement:** 交易服務新增了**合約交易日誌**：使用者收到機器人信號後自己到交易所手動下單，再記下這筆交易的成交、計畫與檢討，
  損益、R 倍數、資金費用、統計與實盤 vs 回測都由交易服務算好。但使用者下單當下多半人在 Claude Code 旁邊，
  要他另開操作台逐格填表，日誌很快就會斷掉；外掛今天完全不認得日誌，助理只能回答「做不到」。
- **Expected Outcome:**
  - 使用者用說的就能記一筆、加成交、改計畫、加附註、寫檢討、查交易、看統計與實盤 vs 回測、管理標籤與手續費率、刪除交易——例如「剛在 97,905 做多 BTC 0.03 顆 10 倍，止損 96,380」。
  - 每一件都以授權給外掛的那位使用者身分進行；交易服務的拒絕原話帶回，「算不出」的數字照交易服務的說法帶回，外掛不算任何一個數字。
  - 助理不拿機器人訊息裡的參考價充當成交價；刪除前先確認是哪一筆。
- **Out of Scope:**
  - 現貨交易日誌。
  - 從交易所匯入成交、代為下單。
  - 由外掛自動把機器人信號記成交易；打開「記到交易日誌」連結（那是操作台的事）。
  - 外掛自己檢查任何日誌規則或計算任何損益與統計。

---

## 2. User Personas

- **Primary Role:** 代使用者操作交易服務的助理（使用者本人透過它說話）；使用者是每週手動下好幾筆永續合約單的交易者。
- **Usage Context:**
  - 下單後幾分鐘內，在 Claude Code 裡口述成交：「剛在 97,905 做多 BTC 0.03 顆 10 倍」。
  - 加碼、減碼、平倉時口述補成交。
  - 週末說「幫我看這週還沒檢討的單」「看這個月績效」，並口述檢討。

---

## 3. User Stories & Acceptance Criteria

以下若無特別說明：使用者帶著有效的外掛授權；使用者的時區為台北（UTC+8）；BTCUSDT 是交易服務認得的合約標的。

### US-01 — 用說的記一筆合約交易 [P0]
**As a** 使用者, **I want** 口述一筆剛下的合約單就記進日誌, **so that** 我不必另開操作台填表。

```gherkin
Scenario: 口述記一筆
  When 使用者說「剛在 97,905 做多 BTCUSDT 0.03 顆 10 倍，止損 96,380」
  Then 交易服務建立一筆持倉中的交易
  And 助理回覆這筆交易的編號、進場均價 97,905、計畫風險，以及記下的成交時間

Scenario: 沒說成交時間以現在為準
  Given 現在是台北時間 09-27 14:03
  When 使用者說「剛在 97,905 做多 BTCUSDT 0.03 顆」，沒說時間
  Then 這筆成交以現在的時刻記下
  And 助理回覆「成交時間記為 09-27 14:03（台北時間）」，請使用者確認

Scenario: 說了成交時間就照他說的
  When 使用者說「今天下午兩點在 97,905 做多 BTCUSDT 0.03 顆」
  Then 這筆成交以台北時間當天 14:00 記下

Scenario: 只貼機器人訊息不當成成交
  Given 使用者只貼上一則合約機器人訊息（參考價 97,850），沒說實際成交價
  When 使用者要求「幫我記一筆」
  Then 助理先問實際成交價與數量，不記下任何交易
  And 不拿參考價 97,850 充當成交價

Scenario: 同標的同方向已有持倉中
  Given 使用者已有 #27 BTCUSDT 做多、持倉中
  When 使用者說「再記一筆 BTC 做多」
  Then 助理帶回交易服務的拒絕：BTCUSDT 做多已有持倉中的 #27
  And 助理建議改成在 #27 加一筆進場成交

Scenario: 關聯自己的合約交易策略
  Given 使用者有自己的合約交易策略「BTC 趨勢跟隨」
  When 使用者說「這筆是照 BTC 趨勢跟隨做的」
  Then 交易關聯到「BTC 趨勢跟隨」

Scenario: 交易服務拒絕時原話帶回
  When 使用者要求記一筆槓桿 0.5 倍的交易
  Then 助理帶回交易服務的原話：槓桿倍數不得小於一
  And 不重送一模一樣的內容
```

### US-02 — 加成交、修正成交 [P0]
**As a** 使用者, **I want** 分批加碼、減碼、平倉時口述補成交, **so that** 日誌和交易所的持倉一致。

```gherkin
Scenario: 加碼
  Given #27 BTCUSDT 做多，持倉 0.030、進場均價 97,905
  When 使用者說「97,960 再加 0.021」
  Then #27 多一筆進場成交
  And 助理回覆持倉 0.051、進場均價 97,927.6

Scenario: 全部平倉
  Given #27 持倉 0.051
  When 使用者說「100,420 全部平掉」
  Then #27 多一筆 0.051 的出場成交，狀態變成已平倉
  And 助理回覆淨損益與 R 倍數，並提醒可以寫檢討

Scenario: 出場超過持倉
  Given #27 持倉 0.031
  When 使用者說「平掉 0.05」
  Then 助理帶回交易服務的拒絕：出場數量超過目前持倉，要反手請先平倉再新增一筆反方向的交易

Scenario: 持倉中修正打錯的成交
  Given #27 持倉中，一筆進場成交記成 97,095
  When 使用者說「那筆進場其實是 97,905」
  Then 那筆成交改為 97,905
  And 助理回覆重算後的進場均價

Scenario: 持倉中刪除一筆記錯的成交
  Given #27 持倉中，有兩筆進場成交
  When 使用者說「第二筆加碼記錯了，刪掉」
  Then 那筆成交刪除
  And 助理回覆剩下的持倉與進場均價

Scenario: 平倉後成交鎖定
  Given #27 已平倉
  When 使用者要求修改其中一筆成交
  Then 助理帶回交易服務的拒絕：平倉後成交已鎖定
  And 建議改成加附註，或刪除整筆重記
```

### US-03 — 計畫、附註與檢討 [P0]
**As a** 使用者, **I want** 口述修改計畫、加附註、寫檢討, **so that** 復盤不必離開 Claude Code。

```gherkin
Scenario: 持倉中修改計畫
  Given #32 持倉中
  When 使用者說「止損改到 3,480」
  Then #32 的計畫止損為 3,480

Scenario: 平倉後修改計畫被拒
  Given #27 已平倉
  When 使用者說「把 #27 的止損改成 96,300」
  Then 助理帶回交易服務的拒絕：平倉後計畫已鎖定
  And 建議改成加附註

Scenario: 加附註
  Given #27 已平倉
  When 使用者說「#27 加個附註：止損其實是 96,300，當時打錯」
  Then #27 多一則附註，計畫止損不變

Scenario: 口述檢討
  Given #27 已平倉
  When 使用者口述檢討，執行評分 4、失誤標「提早出場」
  Then #27 寫下檢討，狀態變成已檢討

Scenario: 持倉中寫檢討被拒
  Given #32 持倉中
  When 使用者要求寫 #32 的檢討
  Then 助理帶回交易服務的拒絕：平倉後才能檢討
```

### US-04 — 查交易、看統計、看實盤 vs 回測 [P0]
**As a** 使用者, **I want** 問一句就看到交易與成績, **so that** 週末復盤能直接在對話裡做。

```gherkin
Scenario: 列出待檢討的交易
  Given 使用者有 4 筆已平倉但還沒檢討的交易
  When 使用者說「這週還沒檢討的單」
  Then 助理列出那 4 筆

Scenario: 列出交易預設最近 20 筆
  Given 使用者有 35 筆交易
  When 使用者說「列出我的交易」，沒說要幾筆
  Then 助理列出第一筆進場最新的 20 筆，並說出總共 35 筆、可以要更多

Scenario: 指定要幾筆
  Given 使用者有 35 筆交易
  When 使用者說「列出最近 30 筆交易」
  Then 助理列出最新的 30 筆

Scenario: 算不出的數字照原話帶回
  Given #31 沒有計畫止損
  When 使用者查看 #31
  Then 助理說 R 倍數「未設止損，算不出」，不說成 0

Scenario: 看統計
  Given 最近 30 天有已平倉交易
  When 使用者說「看這個月績效」
  Then 助理回覆勝率、平均 R、獲利因子、失誤成本、有關聯策略 vs 自行判斷

Scenario: 沒說期間就看最近 30 天
  When 使用者說「看我的績效」
  Then 助理回覆最近 30 天的統計並說出是最近 30 天

Scenario: 期間內沒有已平倉交易
  Given 最近 7 天沒有任何交易平倉
  When 使用者說「看這週績效」
  Then 助理回覆這段期間沒有已平倉交易，勝率不適用

Scenario: 看實盤 vs 回測
  Given 「BTC 趨勢跟隨」有已平倉的 BTCUSDT 實單
  When 使用者說「BTC 趨勢跟隨實盤跟回測比一下」
  Then 助理回覆每個標的一列的實盤與回測平倉筆數、勝率、做多勝率、做空勝率

Scenario: 別人的交易
  Given 交易 #9 屬於另一位使用者
  When 使用者查看 #9
  Then 助理帶回「找不到這筆交易」
```

### US-05 — 標籤與手續費率 [P1]
**As a** 使用者, **I want** 口述管理標籤與手續費率, **so that** 記一筆時手續費與標籤都對。

```gherkin
Scenario: 設定手續費率
  When 使用者說「我的手續費掛單 0.02%、吃單 0.05%」
  Then 交易服務記下這組手續費率
  And 助理說明之後記的成交會依此自動算手續費，已記下的不會改

Scenario: 修正手續費率
  Given 使用者的吃單費率為 0.05%
  When 使用者說「吃單其實是 0.04%」
  Then 吃單費率改為 0.04%

Scenario: 費率為負被拒
  When 使用者說「吃單費率 −0.01%」
  Then 助理帶回交易服務的拒絕：手續費率不得為負

Scenario: 新增型態標籤
  When 使用者說「幫我加一個型態標籤：突破」
  Then 使用者的型態標籤多一個「突破」

Scenario: 標籤重名被拒
  Given 使用者已有型態標籤「突破」
  When 使用者再要求新增型態標籤「突破」
  Then 助理帶回交易服務的拒絕：已有同名的型態標籤

Scenario: 標籤改名
  Given 失誤標籤「移動止損」貼在 4 筆交易上
  When 使用者說「把移動止損改名為放寬止損」
  Then 那 4 筆交易改為帶著「放寬止損」

Scenario: 使用中的標籤刪除被拒
  Given 失誤標籤「移動止損」貼在 4 筆交易上
  When 使用者要求刪除「移動止損」
  Then 助理帶回交易服務的拒絕：還有 4 筆交易貼著它
```

### US-06 — 刪除交易 [P1]
**As a** 使用者, **I want** 說一聲就刪掉記錯的整筆交易, **so that** 可以重記。

```gherkin
Scenario: 確認後刪除
  Given 使用者說「刪掉剛剛那筆」，助理指出是 #33 並經使用者確認
  When 助理刪除 #33
  Then #33 連同成交、附註、檢討一併消失

Scenario: 指的不只一筆時不猜
  Given 使用者有兩筆 BTCUSDT 交易
  When 使用者說「刪掉 BTC 那筆」
  Then 助理列出兩筆請使用者指定，不刪除任何一筆

Scenario: 未確認不刪
  Given 使用者說「刪掉剛剛那筆」
  When 使用者還沒確認是哪一筆
  Then 沒有任何交易被刪除
```

### US-07 — 代辦的共通規矩 [P0]
**As a** 使用者, **I want** 日誌的每一件事都照外掛既有的規矩代辦, **so that** 我知道失敗時該做什麼。

```gherkin
Scenario: 沒有欄位能指定擁有者
  When 助理記一筆交易
  Then 這筆交易屬於授權給外掛的那位使用者，助理沒有任何方式替別人記

Scenario: 交易服務不認得身分
  Given 交易服務判定這份外掛授權已不認得
  When 助理記一筆交易
  Then 助理回覆請使用者到 Claude Code 的外掛選單重新連線，不重試

Scenario: 連不到交易服務
  Given 交易服務暫時不在
  When 助理查看交易
  Then 助理回覆暫時連不到交易服務、晚一點再試同一件事，不說成使用者做錯了
```

## 4. Business Flow & Logic

- **Flow Diagram:**

  ```mermaid
  flowchart LR
    U[使用者口述] --> A[助理挑一件日誌能力並填好內容]
    A --> C{外掛授權有效?}
    C -- 否 --> R1[指出授權說明／請重新連線]
    C -- 是 --> T[以那位使用者身分轉給交易服務]
    T -- 成功 --> OK[帶回交易服務的內容]
    T -- 拒絕 --> NO[原話帶回拒絕原因]
    T -- 連不到 --> DOWN[暫時連不到交易服務]
  ```

- **Core Business Rules:**
  - **能力清單新增的日誌能力**（全部屬於合約那一條線，名字一律帶合約）：記一筆合約交易、加一筆成交、修改成交、刪除成交、修改進場計畫、加附註、寫檢討、
    列出合約交易、查看一筆合約交易、看績效統計、看實盤 vs 回測、列出標籤、新增標籤、標籤改名、刪除標籤、看手續費率、設定手續費率、刪除合約交易。
  - **業務規則全由交易服務決定**：一標的一方向一筆持倉中、不能反手、平倉後成交與計畫鎖定、使用中標籤不能刪、統計口徑、實盤 vs 回測口徑……外掛一條都不檢查、不重算，只原話帶回。
  - **身分**：一律以呼叫帶來的外掛授權進行；沒有任何欄位可以指定擁有者。
  - **成交價**：必須是使用者說的實際成交價；參考價不是成交價，說明裡要寫明助理不得拿機器人訊息裡的參考價充當。
  - **成交時間**：使用者沒說時以現在為準；使用者說的時間以他的時區理解；回覆一律以使用者的時區說出記下的時間讓他確認。
  - **列出交易**：預設第一筆進場最新的 20 筆，可指定筆數與狀態、合約標的、期間篩選；回覆說出總筆數。
  - **統計期間**：沒說即最近 30 天，可選 7／30／90 天或全部，回覆說出是哪一段。
  - **刪除交易**：說明要求助理先向使用者確認是哪一筆；指的不只一筆時列出請使用者指定。
  - **算不出／不適用／估算**：照交易服務的說法帶回，不以 0 代替、不省略原因。
  - **失敗的三種說法**沿用既有外掛規矩：交易服務拒絕原話帶回；不認得身分請到外掛選單重新連線；連不到交易服務請晚一點再試同一件事。
- **Edge Cases:**
  - 使用者口述含糊（沒說方向、數量或價格）→ 助理先問，不猜。
  - 同一句話包含多筆成交（「97,905 買 0.03、97,960 再買 0.021」）→ 第一筆記一筆交易，第二筆加成交；若第一步被拒則停下並帶回原因。
  - 看實盤 vs 回測需要重演 → 可能需要數秒，沿用重演的等待時間。

## 5. UI/UX Design & Interaction

- 外掛沒有畫面；每件能力的說明要讓助理讀懂：哪些欄位必填、方向只有做多與做空、成交時間的時區、參考價不是成交價、刪除前先確認、平倉後鎖定要改用附註。
- 回覆要讓使用者一眼確認記對了：編號、方向、持倉、進場均價、記下的時間（使用者時區）。

---

## 6. Non-Functional Requirements

- **Performance:** 一般日誌能力照一般等待時間；看實盤 vs 回測照重演等待時間。
- **Security:** 外掛授權只確認、不保管，絕不出現在回覆或紀錄裡；沒有指定擁有者的欄位。
- **Compatibility:** 沿用瀏覽器登入取得的外掛授權。
- **Analytics / Tracking:** N/A

---

## 7. Dependencies & Risks

- **External Dependencies:** 交易服務的合約交易日誌（`go-trading` 同名切片）必須先上線；外掛能力清單需與交易服務提供的日誌能力一致。
- **Known Risks:**
  - 助理從口述推斷數字可能聽錯（例如 0.03 顆與 0.3 顆），所以回覆必須復述關鍵數字讓使用者確認。
  - 使用者時區若無從得知，以台北時間為預設並在回覆說出。
