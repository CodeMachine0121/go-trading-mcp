# Product Requirements Document (PRD) — 自動下單限價進場（外掛）

**Status:** Finalized · **Version:** v1.0 · **Owner:** James Hsueh
**Stakeholders:** 交易服務（`go-trading` 同名切片，業務規則的唯一來源）

---

## 1. Background & Goal

- **Problem Statement:**
  交易服務把合約機器人自動下單的**開倉**改成**有上限的限價進場**，並在每台機器人上加了**進場滑價容忍度**；
  下單結果多了進場單的細節與「沒有成交」；進場單還掛在幣安上時不能刪機器人。
  外掛今天既不能替使用者設定容忍度，也沒教助理讀懂新的下單結果；更嚴重的是，外掛各處還在說
  「自動下單目前開著也還不會下單、只送 Telegram 通知」——2026-10-12 合約機器人 #33 已經透過自動下單在幣安上真的開倉、平倉，這句話會讓助理對使用者說錯一件跟真錢有關的事。
- **Expected Outcome:**
  1. 助理建立、改寫機器人時能給進場滑價容忍度；改寫時沒給就保留原值，且說明講清楚這個例外。
  2. 助理查看、列出機器人時看得到並說得出容忍度。
  3. 助理讀執行紀錄時說得出進場單的參考價、限價、要求與已成交數量、滑價（正數對使用者不利）、容忍度與進場單狀態，並認得「沒有成交」。
  4. 刪除被進場單擋下時，助理說得出原因與解法（到網頁關自動下單、等撤單後再刪）。
  5. 外掛裡**沒有任何一處**再說自動下單「還不會下單」；改說合約機器人開著自動下單會真的開倉平倉。
- **Out of Scope:**
  - 下單、撤單、打開或關掉自動下單、存取幣安交易金鑰。
  - 外掛自己檢查容忍度範圍或算任何數字。
  - 現貨自動下單；平倉與止損止盈的任何改變。

---

## 2. User Personas

- **Primary Role:** 代使用者操作交易服務的助理（使用者本人透過它說話）。
- **Usage Context:** 使用者在 Claude Code 裡說「建一台合約機器人、進場滑價最多 0.05%」「上一筆單成交得如何」「刪掉這台」「看一下我的機器人」。

---

## 3. User Stories & Acceptance Criteria

以下若無特別說明：使用者帶著有效的外掛授權。

### US-01 — 設定進場滑價容忍度 [P0]
**As a** 使用者, **I want** 透過助理設定每台機器人能接受多少進場滑價, **so that** 不必開網頁就能調整。

```gherkin
Scenario: 建立時沒提容忍度（例 1）
  When 使用者要求建立一台合約機器人，沒提進場滑價容忍度
  Then 送給交易服務的建立內容不含進場滑價容忍度
  And 能力說明告訴助理沒給就是 0.1

Scenario: 給了容忍度（例 2）
  When 使用者說「進場滑價最多 0.05%」
  Then 送給交易服務的內容帶著進場滑價容忍度 0.05

Scenario: 容忍度 0（例 3）
  When 使用者要容忍度 0
  Then 送給交易服務的內容帶著 0
  And 能力說明告訴助理 0 代表只肯在參考價成交、快速行情裡可能常常不成交

Scenario: 超出範圍（例 4）
  Given 交易服務拒絕超出 0 到 5 的容忍度，說「進場滑價容忍度必須介於 0 到 5 之間（單位：%）」
  When 使用者要 6%
  Then 助理拿到的是交易服務那句原話
  And 能力說明事先寫明範圍是 0 到 5（含）、單位是百分點

Scenario: 改寫時沒給就保留（例 5）
  Given 一台已停止的機器人，進場滑價容忍度 0.3
  When 使用者只要求把觸發間隔改成 15 分鐘
  Then 送給交易服務的改寫內容不含進場滑價容忍度
  And 改寫能力的說明寫明「整份改寫」的例外包括進場滑價容忍度：不給即保留原值
```

### US-02 — 看得到容忍度 [P0]
**As a** 使用者, **I want** 查看機器人時知道它的進場滑價容忍度, **so that** 我知道它開倉最多容許多少滑價。

```gherkin
Scenario: 查看一台（例 6）
  Given 機器人的進場滑價容忍度是 0.2
  When 使用者問「這台的設定」
  Then 交易服務回覆的容忍度原樣交給助理
  And 查看與列出機器人的能力說明都提到這一格與它的意思
```

### US-03 — 讀懂下單結果 [P0]
**As a** 使用者, **I want** 助理說得出每一筆自動下單的進場怎麼成交, **so that** 我知道滑價有沒有吃掉我的利潤。

```gherkin
Scenario: 全部成交（例 7）
  Given 一輪的下單結果：參考價 84154、限價 84238.1、成交 0.002 @ 84180、滑價 0.031、進場單全部成交
  When 使用者問「上一筆單成交得如何」
  Then 能力說明讓助理說得出「全部成交、比參考價貴 0.031%（對你不利）」

Scenario: 部分成交（例 8）
  Given 一輪的下單結果：要求 0.002、已成交 0.001、進場單部分成交
  When 使用者問同一句
  Then 能力說明讓助理說得出「部分成交 0.001／0.002，其餘已撤單」

Scenario: 沒有成交（例 9）
  Given 一輪的下單結果是「沒有成交」
  When 使用者問同一句
  Then 能力說明讓助理說得出「進場單沒有成交、已撤單，沒有開倉」

Scenario: 等待成交中（例 10）
  Given 一輪的下單結果是「等待下單」、進場單等待成交、已成交 0
  When 使用者問同一句
  Then 能力說明讓助理說得出「進場單還在等成交，最多等一個觸發間隔」
```

### US-04 — 刪除被擋下時知道怎麼辦 [P1]
**As a** 使用者, **I want** 助理說清楚為什麼刪不掉, **so that** 我知道下一步。

```gherkin
Scenario: 進場單還掛著（例 11）
  Given 機器人有一張進場單掛在幣安上
  When 使用者要求刪除這台機器人
  Then 助理拿到交易服務的拒絕原話與它的原因「進場單還掛在幣安上」
  And 刪除能力的說明告訴助理：請使用者自己到網頁上關掉這台的自動下單、等進場單撤掉後再刪，外掛不能替他關

Scenario: 沒有掛著的進場單（例 12）
  Given 機器人沒有掛著的進場單
  When 使用者要求刪除這台機器人
  Then 照常刪除
```

### US-05 — 說自動下單時說實情 [P0]
**As a** 使用者, **I want** 助理說的自動下單與實際一致, **so that** 我不會以為開著的機器人不會動我的錢。

```gherkin
Scenario: 列出機器人（例 13）
  Given 合約機器人甲自動下單開著
  When 使用者說「看一下我的機器人」
  Then 能力說明讓助理標出「自動下單：開」，並說明它會真的在幣安上開倉與平倉
  And 外掛的任何說明與給助理的整體指引都不再出現「還不會下單」

Scenario: 要求打開自動下單（例 14）
  When 使用者說「幫我把甲的自動下單打開」
  Then 助理說明只能在網頁的機器人詳細頁自己做
  And 不送出任何改動
```

## 4. Business Flow & Logic

- **Core Business Rules:**
  - **進場滑價容忍度**：百分點，0～5（含）；建立不給即 0.1；改寫不給即保留；外掛不給就不送、不替助理填預設值，也不檢查範圍。以文字形式的精確小數交給交易服務（與其他數字欄位一致）。
  - **改寫機器人**照舊是整份改寫，例外有三：行情種類、自動下單、進場滑價容忍度——都是不給即保留。
  - **下單結果**原樣轉交；外掛只在說明裡講清楚每一樣的意思，不算、不改寫。
  - **刪除被擋**的拒絕原話與原因原樣轉交。
  - **自動下單的說法**：合約機器人開著自動下單時會真的在使用者的幣安帳戶上開倉（有上限的限價進場單）與平倉（立刻以市場價成交），並掛止損止盈；現貨機器人目前仍不下單。切換開關與金鑰只能在網頁上由使用者自己做。
- **Edge Cases:**
  - 交易服務還沒更新到這一版：建立／改寫帶了容忍度會被忽略或拒絕，照原話轉述。
  - 更早的執行紀錄沒有進場欄位：沒有不代表那一輪沒下單。

## 6. Non-Functional Requirements

- **Security:** 外掛照舊不能下單、撤單、切換自動下單，也不經手幣安金鑰。

## 7. Dependencies & Risks

- **External Dependencies:** 交易服務 `auto-order-limit-entry` 切片已上線。
- **Known Risks:** 外掛先部署、交易服務還沒部署時，容忍度欄位不會生效；兩邊應一起部署。
